## 1. 项目概述

### 1.1 一句话定义

一个面向中文读者的 AI 论文阅读站，把**每周新论文**与**领域经典论文**放进同一个界面体系，并为每篇论文提供结构化、可快速理解的深度解读。

### 1.2 要解决的问题

- **信息过载**：AI 论文以每周数百篇的速度产出，研究者与从业者无法判断该读什么。
- **阅读门槛高**：论文原文冗长，非本方向读者难以在 5 分钟内抓住核心。
- **经典与前沿割裂**：新论文的意义往往需要放回经典脉络中才能理解，但两者通常散落在不同地方。
- **中文深度内容稀缺**：新论文多为英文，中文解读质量参差且分散在公众号、推文、论坛。

### 1.3 目标用户

| 用户 | 场景 | 核心诉求 |
|---|---|---|
| AI 从业者 / 工程师 | 通勤或周末补论文 | 快速判断这篇值不值得深读 |
| 研究生 / 学生 | 入门新方向 | 有一条从经典到前沿的阅读路径 |
| 研究者 | 追踪同行进展 | 按周回看，不漏掉重要工作 |
| 技术管理者 | 把握技术趋势 | 看方向分布与演化，而非单篇细节 |

### 1.4 非目标（本期不做）

- 用户账号体系、付费墙
- 论文全文托管与 PDF 渲染（一律跳转第三方原文）
- 社区评论、打分
- 自动抓取论文 PDF 并解析全文
- 多语言（除中英标题并对外只做中文）

## 2. 功能需求

整体分三个模块，共享同一套论文数据模型与同一套阅读器。

```
                    ┌──────────────────────────┐
                    │      论文阅读器 (M3)      │
                    │  摘要 / 创新点 / 方法 /   │
                    │  结论 / 思维导图          │
                    └───────▲──────────▲───────┘
                            │          │
              ┌─────────────┴───┐  ┌───┴─────────────┐
              │   每周档案库 M1  │  │   经典论文库 M2  │
              │  按日历周编排    │  │  按方向/年代编排  │
              └─────────────────┘  └─────────────────┘
```

### M1 · 每周论文档案库（Weekly Archive）

**定位**：按日历编排的滚动论文清单，每周更新。

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| M1-1 | 按 ISO 周（周一至周日）分卷归档 | P0 | 每周一个卷宗，URL 形如 `/archive/2026-W35` |
| M1-2 | 卷宗内按发布时间倒序，扁平连续编号 | P0 | 编号 `01, 02, 03...`，跨天连续不重置 |
| M1-3 | 卷宗首页展示时间窗与论文总数 | P0 | 顶部统计条：论文数 / 来源数 / 覆盖天数 / 精选数 |
| M1-4 | 左侧时间轴 + 右侧论文卡片布局 | P0 | 参考 `reference/weekly-archive-prototype.html` |
| M1-5 | 时间轴按天分组，日期印章滚动吸顶 | P0 | 左侧显示 `08-30 / 周日 / N 篇` |
| M1-6 | 论文卡片要素完整 | P0 | 序号、中文标题、来源徽章、相对时间、≤200 字摘要、跳转链接 |
| M1-7 | 来源生成简洁徽章并按家族着色 | P1 | X / HuggingFace / Hacker News / 实验室官方 / 媒体 各有配色 |
| M1-8 | 编辑精选标记 | P1 | 进入精选池的条目带「精选」徽章 |
| M1-9 | 关键词搜索（标题 + 摘要） | P1 | 前端过滤，无需后端 |
| M1-10 | 按来源筛选（chips，带篇数） | P1 | 与搜索可叠加 |
| M1-11 | 周与周之间可前后翻页 | P1 | 上一周 / 下一周，最新卷为默认入口 |
| M1-12 | 空结果态 | P2 | 无匹配时给出提示与重置入口 |
| M1-13 | 滚动渐入动画 | P2 | IntersectionObserver，尊重 `prefers-reduced-motion` |

**数据规模现实约束（重要）**

第一版数据源为 AI HOT。实测单周窗口内该源的论文条目量约 **200+ 篇**，其中进入编辑精选池的通常只有个位数。因此卷宗规模策略为：

- 每卷收录 **40—60 篇**，选取规则为「窗口内综合评分最高的 N 篇，且必须包含全部编辑精选条目」。
- 展示顺序严格按时间倒序，**不按评分排序**（避免变成热度排行榜）。
- 卷宗页脚必须如实披露：窗口内总数、本卷收录数、选取规则、精选篇数。

### M2 · 经典论文库（Classic Papers）

**定位**：AI 领域奠基与里程碑论文的结构化清单，人工策划、长期维护。

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| M2-1 | 收录并处理 `data/classic-papers.json` 中的 95 篇 | P0 | 数据已就绪，含中英标题、作者、年份、venue、arXiv、贡献、影响 |
| M2-2 | 按方向（track）分栏浏览 | P0 | 11 个方向：基础 / 架构 / 预训练 / 规模 / 对齐 / 推理 / 效率 / 生成 / 视觉 / RL与Agent / 可解释性 |
| M2-3 | 按重要度（tier）筛选 | P0 | `seminal` 奠基 / `milestone` 里程碑 / `essential` 必读 |
| M2-4 | 按年代时间轴视图 | P1 | 1958 → 2025，展示技术演进脉络 |
| M2-5 | 论文详情页 | P0 | 元数据 + 贡献 + 影响 + 前置知识 + 相关论文，入口跳阅读器 |
| M2-6 | 前置知识 / 相关论文图谱跳转 | P1 | 基于 `prerequisites` 与 `related` 字段做双向链接 |
| M2-7 | 推荐阅读路径 | P2 | 例如「Transformer 入门五篇」「扩散模型入门五篇」等策展列表 |
| M2-8 | 与每周档案库的条目做关联提示 | P2 | 新论文卡片上若与经典论文同名/同主题，给出「关联经典」提示 |

**已收录清单概览**：95 篇，其中奠基之作 29 篇、里程碑 44 篇、必读 22 篇；年代分布为 2010 年代 27 篇、2020 年代 64 篇，另有 1958—1998 的 4 篇历史源头。完整清单见 `docs/CLASSIC-PAPERS.md`。

### M3 · 论文阅读器（Paper Reader）

**定位**：站内所有论文（每周新论文 + 经典论文）的统一深度阅读界面。

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| M3-1 | 统一路由 | P0 | `/paper/[id]`，每周论文与经典论文共用同一组件 |
| M3-2 | 摘要（Abstract） | P0 | 中文，≤200 字，来自数据源或 LLM 生成 |
| M3-3 | 核心观点 / 创新点 | P0 | 3—5 条要点列表，每条一句话 |
| M3-4 | 主要方法 | P0 | 用结构化区块描述：问题 → 方法 → 关键设计 → 实验设置 |
| M3-5 | 结论与影响 | P0 | 论文自身的结论 + 对领域的后续影响 |
| M3-6 | 思维导图 | P0 | 可交互的树状图，见下方专门说明 |
| M3-7 | 原文跳转 | P0 | 站内解读页 + 第三方原文，均新标签打开 |
| M3-8 | 元数据区 | P0 | 标题（中/英）、作者、年份、venue、arXiv 编号、方向标签 |
| M3-9 | 阅读进度与目录 | P1 | 右侧 sticky 目录，高亮当前区块 |
| M3-10 | 术语浮层解释 | P2 | 关键术语 hover 显示一句话解释 |
| M3-11 | 深浅色切换 | P2 | 默认浅色科技蓝 |

**思维导图（M3-6）专门说明**

思维导图必须满足：

1. **数据驱动**：以 JSON 树结构存储，字段为 `{ id, label, type, children, note }`，`type` 取值 `root | problem | method | contribution | result | impact`。
2. **可交互**：支持节点展开/折叠、点击节点在右侧联动显示该节点的 `note` 说明、缩放与拖拽平移。
3. **纯客户端渲染**：不依赖外部 CDN。推荐 Mermaid（构建期转 SVG）或自研 SVG 布局；若引入第三方库必须本地打包，禁止运行时外链。
4. **移动降级**：窄屏下自动切换为缩进式大纲列表，不做横向滚动。
5. **可访问性**：提供「查看大纲文本」按钮，输出纯文本层级结构。

## 3. 数据模型

### 3.1 统一论文记录（PaperRecord）

三个模块共用一套核心模型，见 `data/schemas/paper-record.schema.json` 的完整定义。核心字段：

```ts
type PaperSource = 'aihot' | 'arxiv' | 'manual' | (string & {});

interface PaperRecord {
  id: string;              // 全局唯一，slug 形式
  kind: 'weekly' | 'classic';
  title: string;           // 中文标题（展示主标题）
  titleEn?: string;        // 英文原标题
  authors?: string[];
  year?: number;
  venue?: string;
  arxivId?: string;
  source: {
    name: string;          // 来源显示名，如 "HuggingFace Daily Papers"
    family: PaperSource;   // 用于徽章配色的家族标识
    url?: string;
  };
  timelineAt: string;      // ISO 8601，用于排序与时间轴归位
  publishedAt?: string;    // 第三方原文发布时间，可能缺失
  curated: boolean;        // 是否进入编辑精选
  tags: string[];
  links: {
    reader: string;        // 站内阅读器路径，必有
    original: string;      // 第三方原文，必有
    detail?: string;       // 数据源详情/中文阅读页
  };
  summary: string;         // ≤200 字中文摘要
  reading?: ReadingContent; // 阅读器深度内容，见 3.2
}
```

### 3.2 阅读器内容（ReadingContent）

```ts
interface ReadingContent {
  abstract: string;                 // ≤200 字
  keyPoints: string[];              // 3—5 条核心观点/创新点
  method: {
    problem: string;                // 要解决什么问题
    approach: string;               // 整体思路
    design: string[];               // 关键设计（2—5 条）
    setup?: string;                 // 实验设置
  };
  conclusion: {
    findings: string;               // 论文结论
    impact: string;                 // 对领域的影响
    limitations?: string;           // 局限
  };
  mindmap: MindmapNode;             // 思维导图树
  status: 'draft' | 'reviewed';     // 内容生产状态
  generatedBy?: 'llm' | 'manual';
  reviewedAt?: string;
}

interface MindmapNode {
  id: string;
  label: string;
  type: 'root' | 'problem' | 'method' | 'contribution' | 'result' | 'impact';
  note?: string;
  children?: MindmapNode[];
}
```

### 3.3 卷宗（WeeklyVolume）

```ts
interface WeeklyVolume {
  isoWeek: string;        // "2026-W35"
  startDate: string;      // 周一，YYYY-MM-DD
  endDate: string;        // 周日，YYYY-MM-DD
  windowStart: string;    // 实际数据时间窗起点
  windowEnd: string;      // 实际数据时间窗终点
  poolTotal: number;      // 窗口内数据源条目总数
  paperCount: number;     // 本卷收录数
  curatedCount: number;   // 其中精选数
  sourceCount: number;
  selectionRule: string;  // 人类可读的选取规则说明
  papers: string[];       // PaperRecord.id 的有序数组
}
```

## 5. 数据接入

第一版接入 AI HOT，但**必须按可插拔适配器设计**，见 `docs/DATA-SOURCES.md`。要点：

- 每个数据源实现统一 `SourceAdapter` 接口：`fetch()` → 原始条目 → `normalize()` → `PaperRecord`。
- 新增数据源只需新增一个适配器文件并在注册表登记，不改动页面与数据模型。
- 抓取脚本独立于 Web 应用，产物为版本化的 JSON 文件，提交进仓库（内容即数据，便于审计与回滚）。
- 抓取与生成脚本放在 `scripts/`，不进入前端 bundle。

## 6. 内容生产流程

阅读器的深度内容采用「LLM 生成 + 人工审核入库」，详见 `docs/CONTENT-PIPELINE.md`。要点：

1. 脚本读取论文元数据与可获取的摘要/正文片段，调用 LLM 生成 `ReadingContent` 草稿，写入 `content/draft/`。
2. 人工审核（重点核对创新点、方法细节、数字结论），通过后移入 `content/reviewed/` 并置 `status: reviewed`。
3. 只有 `status: reviewed` 的内容才对线上可见；草稿态在 UI 上显式标注「自动生成，未经审核」。
4. **所有数字、指标、结论必须能回溯到原文**，无法核实的必须删除而非保留。

## 7. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 首屏 LCP < 2.5s；卷宗页静态生成，列表不在客户端做虚拟滚动以外的重计算 |

| 更新频率 | 每周一生成上一周卷宗；经典论文库按需增量 |

## 10. 风险与开放问题

| 风险 | 影响 | 应对 |
|---|---|---|
| AI HOT 窗口内条目质量参差 | 卷宗噪音大 | 坚持评分阈值 + 精选兜底；页脚披露选取规则 |
| LLM 生成的解读存在幻觉 | 内容可信度受损 | 强制人工审核；数字结论必须可回溯原文；草稿态显式标注 |
| 每周量大导致人工审核跟不上 | 更新停滞 | 内容深度分层：新论文先给摘要级，深度解读按优先级排期 |
| 数据源 API 变更或限流 | 抓取失败 | 适配器隔离 + 抓取失败保留上一卷，不产出空卷 |
| 思维导图库体积影响首屏 | 性能劣化 | 优先轻量自研 SVG 布局；若用 Mermaid 则仅在该路由懒加载 |

**待确认问题**

1. 卷宗规模：40、50 还是 60 篇？（当前按 50 实现）
2. 是否需要 RSS / 邮件订阅？（PRD 暂按提供 RSS 处理）
3. 经典论文库是否接受社区提 PR 补充？（涉及维护成本）
4. 站内搜索是否需要跨卷历史检索？（当前只做卷内过滤）
